# RelBench 质量与代价联合优化（2026-11-12）

用户要求先拉取最新代码和论文，定位 RelBench 质量退化的原因，在保住前六列代价优势的同时提高六项任务的预测质量。当前候选的目标、预算、数据边界和接纳标准见 `protocol.json`。本目录是开发试验记录；完成全部检查之前不替换论文数值。

- 主仓库基线：`b60a84b`；论文仓库 `main`：`ec8d7559b6406c92800dd50e56d14d864b2bf9c6`。在独立工作目录开发，保留原工作区及服务器未提交修改。
- 原始运行：noctis `/root/agentdb-mid/results/relbench-pilot3/` 与 `results/relbench-main/`。
- `tools/relbench/diagnose-quality.py` 只读既有会话，逐文件记录 SHA-256，输出逐截点质量、第一次验证是否达标、验证次数、停止原因及提炼失败。诊断输出中的测试分数不进入优化器。
- `mavra-push` 的 24 个复用会话中，23 个第一次有效验证就达到本组上一期方案的目标。user-badge 的空记忆首期测试 AUC 已低于无记忆，随后差距持续；study-adverse 四个复用会话中三个只验证一次。
- 已有 `mavra-select` 能降低 token，但额外 SQL 在较慢的定义上耗尽 600 秒超时，不能满足所有代价约束；`mavra-select2` 的正式运行此前被取消，保留其代码和试跑记录。

## 候选方法

1. 同表、同过滤、同关联、同实体映射、同时间上界与窗口的聚合共享一次扫描。不同输入关系和非聚合表达式保持独立。保留输出顺序、名称、空值与填充值。
2. 首期以经过审计的实体表方案作保底，在两次互不可见的探索中按验证分数选择。兄弟任务只提供定义键和含义，避免把它的完整方案当成本任务的强制起点。两次探索的全部代价均计入。
3. 复用起点保留原方案，并在已有特征矩阵上试少量按增益排序的子集，采用固定学习器和验证分数选择；不增加模型请求，不重算相同的特征矩阵。筛选有时间预算，原方案始终保留为回退。
4. 新臂 `mavra-budgeted` 每个复用会话至多三次模型调用、六次智能体工具调用。慢方案有独立语句时间上限。选择、额外拟合、查询及失败尝试的耗时均保留在会话记录中。

## 第二候选：互补特征组合与已定位泄漏列的投影

`mavra-budgeted` 完整运行时保持源码不变。第二候选 `mavra-portfolio` 在独立工作目录开发；设计时间及数据边界见 `v2-plan.json` 和 `protocol-v2.json`。截至提出该候选时，第一候选只查看了训练／验证记录，测试评估尚未进行。

- 首期保留两次探索各自最好的特征矩阵。按训练增益取第二次探索的至多 40 个候选，对训练和验证值都相同的列逐值去重。在固定学习器的一次联合拟合中排序，最多再试三个不超过 100 列的组合；按验证分数选择，未超过容差时保留原来的单次方案。组合 SQL 须在检查种子上重现矩阵值并通过新的泄漏审计。
- 运行中发现，user-engagement 一次探索的七次有效执行均被泄漏审计拒绝，最后定位到 `account_age_days` 一列。第二候选只对审计明确指出的输出列尝试删除；剩余输出须重新做 SQL 值比较和泄漏审计，再重新拟合。审计出错、不明确或新检查不通过时继续拒绝；不将失败审计视作安全证据。

- 离线检查：29 项 Python 检查通过；另有一项真实 PostgreSQL 检查验证不同输出键名、不同返回顺序和同实体多个时间点下，组合 SQL 仍逐值重现缓存矩阵。固定学习器的合成互补信号检查只验证实现，不作为 RelBench 质量证据。

## 第四候选：保留本期已审计的完整重训结果

第一候选 study-outcome k2 的完整旧方案已经在本期重训达到验证 AUC 0.663516；接着在起点选择时重复执行，同一 SQL 超过 45 秒便退成一列已提炼定义，验证 AUC 只有 0.545633。`mavra-cached` 将本期重训的训练／验证矩阵、增益和完整 SQL 留到本会话，须匹配任务、截点、前期 SQL 及全部种子顺序和标签，且原 SQL 本期审计为 clean。它可直接复用已算好的完整值，免去重复执行与不必要的可执行性探测；较慢原 SQL 不再仅因第二遍时限而退成不完整定义。

这项前置工作全部收费：`charged_current_refit` 记录每次前期方案重训（包括失败尝试）的全部非审计耗时和拟合，追加到本组智能体时间与拟合记录，且只计一次。既有表格对各组共同计算的目标重训不收费；新候选主动为其算法用到的重训加上费用，不能把预计算当作免费缓存。快 SQL 可在矩阵上再做一次有预算的列筛选，改动后的 SQL 必须重现取值并重新通过审计；慢 SQL 保留完整起点，新增智能体方案继续受逐语句时限约束。

设计依据是训练／验证中的超时回退记录（`v4-plan.json`、`protocol-v4.json`）。提出第四候选时第一版测试评估已经开始且部分日志分数可见，须按事后开发披露；不把旧测试集当作一个新的独立留出集。前三组完整结果保持原样。

启动前再检查了少数列泄漏的路径：仅投影掉审计明确指出的坏列，对剩余 SQL 做新的值重现与完整审计，重新拟合后保留其完整剩余矩阵；失败／未知仍拒绝，新增工作仍全部计费。最初 v4 的两个排队进程在任何会话／模型调用前停止，准备资料原样保留；修订后的完整运行 `v4b` 用独立源码目录，见 `v4b-plan.json`。

## 第五候选：常数默认模型只兜底，不预占最佳方案

检查前四版首期记录发现，site-success 的实体表保底没有任何变化的数值列。预先把它设成最佳方案，会使略差的实际特征方案直接累积 patience，而不是先完成一个有效的特征起点。第五候选 `mavra-signal` 在第四版基础上只修正这一初始化规则；`v5-plan.json` 在代码和模型调用之前记录，`protocol-v5.json` 保留相同质量／成本门槛。
